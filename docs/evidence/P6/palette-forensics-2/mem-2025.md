# Palette forensics, claude-mem 2025 slice

## Plain-English answer first

In 2025, Lightwave and the early K1 firmware had two related colour faults, and memory records a fix for each.

1. **Colour came from too few "notes".** On 20 Sep 2025 the Captain said the firmware ran 64 frequency bins but coloured them with `note_colors[i % 12]`. That reused 12 colours about five times along the strip, wasting about 81 % of the colour resolution. Separately, palette lookups were clamped to the middle of the palette (LUT index 128), so palettes "parked" instead of sweeping. The same day, Codex:
   - replaced the 12-colour wheel with a per-bin mapper (`hue_from_mapping`, with linear, log and musical curves; log is the default);
   - removed the mid-point clamp.

   This happened in `clean_aee6631`. That code (`palettes_bridge.h`, `palette_luts.cpp`, `hsv_or_palette`) is the same code K1-09 was built on two days later.
2. **Averaging washed colour out.** Waveform, Bloom and Snapwave added the colours of all 12 chroma notes together (sum, normalise, clamp). With several notes active, the result went grey or white, or became one flat sheet. The recorded fixes all replace averaging with selection:
   - Bloom: the top 3 peaks, then the single dominant peak (Lightwave, 12 Aug 2025);
   - Waveform: the dominant chroma bin (K1-09, 27 Sep 2025);
   - Snapwave: the top 2 peaks was offered (3 Oct 2025); on 19 Nov 2025 Snapwave went back to pure HSV.

**What the 2025 record does not contain.** The phrase "over-averaging" never appears anywhere in claude-mem, in any year (0 hits). No 2025 record states "palette not mapped to each of the 80 bins". The closest match to "80" is that the K1 at the time had **80 logical pixels per half-strip**, mirrored to 160: `LOGICAL_LEDS = 80`, "spread 64 bins over 80 LEDs" (Captain prompt P3186, 28 Sep 2025). [INFERENCE] The Captain's "80 bins" most likely means those 80 per-half pixel positions.

The definitive SpectraSynq_K1_Firmware fix is outside this slice. That repository was only forked from SensoryBridge on **23 Jun 2026** (obs #68197). The fix the previous agent found, `ae5d90a`, is dated 2 Jul 2026.

## THE FIX (as recorded in 2025)

### Fix A: per-bin colour mapping replaces the 12-note modulo (K1 lineage, 20 Sep 2025)

**The problem, in the Captain's words.** [FACT] Prompt P1330, 2025-09-20 20:06 local, cwd `/Users/spectrasynq/Workspace_Management/Software/clean_aee6631`:

> "With 64 frequency bins, they're doing 64 Goertzel calculations every frame, getting 64 distinct frequency magnitudes, and then... **using only 12 colors that repeat**. … 64 bins → 12 colors (modulo wrapping) — **81.25% of potential color resolution wasted** — Same 12 colors repeat ~5.3 times across the display … Instead of: `led_hue = note_colors[i.getInteger() % 12];` They could do: `led_hue = i / 64.0;`"

**Codex agrees.** [FACT] Obs #13744 (2025-09-20T12:06Z, clean_aee6631):

> "The current `% 12` logic is what collapses everything back to the same chromatic scale over and over. It was a safety net during the 96‑bin experiment; now it's just handcuffs. … Patch the waveform and other spectrum modes so they map `bin_index → hue` directly (or via a 64‑entry gradient), no more `% 12`."

**A second fault: the palette parks at the midpoint.** [FACT] Obs #13760 (15:18Z):

> "`src/palettes/palettes_bridge.h:1` now returns LUT colors in palette mode … Auto shift uses a fixed index (128) so colors don't drift."

[FACT] Obs #13762 (15:34Z): "locking auto-shifted palettes to the mid index so they stop drifting." [FACT] Obs #14353 / #14627 (K1-09, 24–25 Sep) still describe a "steady mid index" and "locking the LUT index".

**The fix landed.** [FACT] Obs #13774 (2025-09-20T18:28Z), verbatim:

> "Hue mapping now rides on the new 64-bin spectrum instead of the old 12-step wheel.
> - `src/globals.h:96-124` adds the `HueMapMode` enum plus log-range globals, so hue selection can switch between linear, log-rescaled, or musical palettes.
> - `src/core/globals.cpp:328-347` defines those globals (defaulting to the log curve) and still holds the original 12-note colour wheel for musical blending.
> - `src/system.h:226-323` now saves the Goertzel k value for each bin and, after coefficients are computed, derives the min/max log frequencies used by the new mapping.
> - `src/lightshow_modes.h:22-216` picks up helper functions (`hue_from_mapping`, etc.) and rewires `light_mode_gdft` so `chromatic_mode` pulls hues from the 64-bin mapper instead of the old 12-note interpolation."

[FACT] Obs #13776 (19:00Z), verbatim:

> "**GDFT Hue Flow** (`src/lightshow_modes.h:22-216`): added a reusable `hue_from_mapping()` helper and updated `light_mode_gdft`, `light_mode_chromagram_gradient`, and `light_mode_chromagram_dots` so chromatic paths pull hues from the 64-bin mapper; palette modes now add `hue_position` so auto shift actually moves colour again.
> **Palette Freedom** (`src/palettes/palettes_bridge.h:1-60`, `src/palettes/palette_profiler.h:136-170`): removed the mid-point clamp and no-op'd the chromatic guard … palette colours should now sweep smoothly instead of parking at index 128."

[FACT] Obs #13777 says `src/main.cpp:356-632` "no longer gates the shift on `PALETTE_INDEX == 0`".

[FACT] Obs #13784 (19:47Z): "remapped the hue pipeline everywhere so palettes and the secondary channel ride the same 64‑bin engine … stored per-bin `k`, precomputed the log span, and defaulted the hue mapper to the log curve."

**The mapping formula.** [FACT] Obs #13765 (17:08Z) sets out the design: "Mapping bin index to hue linearly (`i / 64.0f`) is easy but not perceptually uniform … Offer multiple mappings (linear, log, 'Musical')." [INFERENCE] The log mapper normalises each bin's frequency (from its stored Goertzel k) between the precomputed min and max log frequency. No record quotes the exact formula.

**Captain feedback.** [FACT] Obs #13778 opens "AWESOME. That's the glimpse we've been chasing." That is Codex replying to Captain approval. The Captain's prompt text was not captured.

**What was not done.** [FACT] Obs #13776 says the chromagram modes "still lean on the 12-note wheel for hue".

**Prerequisite bug in the same thread.** [FACT] Obs #13765: `NUM_FREQS` is 64, but `notes[]` has only 48 entries. "The clamp in `precompute_goertzel_constants()` now forces bins ≥48 to reuse the last value. That collapses the top 16 bins onto 830 Hz." Obs #13766 prescribes a generated table of 64 unique frequencies.

### Fix B: stop averaging the chroma bins into one colour (several modes, Aug–Nov 2025)

[FACT] Obs #28764 (2025-08-08T21:47Z, Lightwave/LightwaveOS, project "cursor"):

> "Removed normalization — Don't normalize `sum_color` by total magnitude; lets multiple peaks co-exist with distinct strength instead of averaging to a uniform hue."

[FACT] Obs #30094 (2025-08-12T03:11Z, cursor session `cursor-d68463a3…`):

> "Bloom mode updated to avoid flat yellow sheet: Uses top-3 chromagram peaks instead of averaging all bins. Peak-weighted blending retains distinct hues and breaks in propagation. Removed single-hue override when chromatic_mode is off."

[FACT] Obs #30095 (same session): "Use the single dominant chroma peak (not an average) to keep saturated hues. Enforce a saturation floor in Bloom."

[FACT] Obs #15099 (2025-09-27T09:11Z, cwd `/Users/spectrasynq/Workspace_Management/Software/K1-09`):

> "The 'all white' look traced back to the colour blend inside the ported waveform effect. We were averaging the 12 chroma bins, dividing by a coarse normaliser, and then clamping each RGB channel independently to 255. … now rescale the accumulated RGB vector proportionally whenever it would overflow (`src/VP/effect_registry.cpp:179-206`)."

[FACT] Obs #15100 (09:15Z):

> "Waveform colour now follows the dominant chroma bin instead of averaging everything, preserving palette hue and smoothing transitions by blending with the previous frame … (`src/VP/effect_registry.cpp:167-208`)."

[FACT] Obs #15934 (2025-10-03T01:50Z, LightwaveOS_Official), on the Snapwave secondary going white:

> "summing many chroma notes tends to wash to white … Option B: compute SNAPWAVE color from the top 1–2 chroma peaks instead of summing all bins … mix them weighted by their magnitudes."

The record does not say which option the Captain chose.

[FACT] Obs #20613 (2025-11-19T18:56Z, LightwaveOS_Official) is a revert, not a palette fix:

> "Replaced `get_mode_color(...)` inside the Snapwave chroma loop with the original `hsv(SQ15x16(prog), frame_config.SATURATION, SQ15x16(bright))` … without the new palette / get_mode_color layer that was flattening things."

## Method and limits

- claude-mem MCP `search` (single terms, 2025 date filters), `timeline` and `get_observations` were used for the first passes.
- For full coverage I then ran read-only SQL against `~/.claude-mem/claude-mem.db` (`?mode=ro`):
  - regex over every pre-2026 observation, user prompt and session summary;
  - a 70-term coverage count (palette, averaging, bins, 80, NUM_FREQS, hue, gradient, mapping, per-bin, progress, LUT, centroid, dominant, washed, uniform, flat, and the rest of the brief's list).
- The bare term "over-averaging" has 0 hits in all years.
- A memory hook reported `MEMORY_MODE=DEGRADED` (liveness watchdog heartbeat stale). Search and SQL reads still returned data. Hindsight `recall` worked, but it only returned this session's own notes plus the 2026 `ae5d90a` claim, so it added no 2025 evidence.
- Labels: [FACT] means verbatim in a claude-mem record. [INFERENCE] means my reading. "Fixed" means the agent of the time claimed it; no record shows device-verified acceptance in 2025, except #13778, which implies Captain approval of Fix A.
