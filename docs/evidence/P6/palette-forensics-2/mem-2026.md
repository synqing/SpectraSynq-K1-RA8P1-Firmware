## THE FIX

### In plain English
The record contains three separate "palette is not mapped accurately" fixes. The one that matches the Captain's memory is the **16-bucket palette averaging**:
- FastLED's `CRGBPalette16` squashed every palette into 16 averaged slots.
- The position along the palette was rounded to a byte, and the colour came back as 8-bit.
- So the 80 frequency bins, which walk along the palette, never got the palette's real colours.

On 11 Jun 2026 this was replaced by sampling the palette's true colour stops directly, in floating point. On 22 Aug 2026 the literal 80-bin spectrum mode (GDFT) was moved onto that sampler. The previous agent missed this fix. The 12-note chroma problem it found is a different, later problem.

### Fix A — HD palette sampling: 16-slot averaging removed [FACT]

**Captain's trigger, 11 Jun 2026, P113956/P113957:**
- "it's still tending towards white and doesn't seem to display the whole range of the palette … a parameter modification that resulted in significantly more resolution"
- "What other methods or strategies could we possibly consider implementing to get the maximum resolution of the palettes across all effects?"

**What was wrong** (obs #63571 and #73581, quoted):
- "CRGBPalette16 bakes all gradient stops into 16 entries … the palette coordinate was passed as uint8 … CRGB output was 8-bit."
- "Every gradient stop's position is mapped to a palette slot index via integer division by 16 (`indexstart / 16`) … Any two stops falling in the same bucket produce a single palette entry; the finer color detail between them is lost."
- `ColorFromPalette` then gives only "16 blend steps between adjacent palette entries" (#73582, #110130).

**What resolved it** (obs #63568, #63569, #63571, #63574; test `tests/test_palette_hd_static.py`, #63570):
- `PAL_HD_MAX_STOPS 48` and `struct PaletteStopsHD {count; float pos[], r[], g[], b[]}`.
- `palette_hd_unpack()` reads the raw gradient bytes and stops at `idx==255`. It runs once per palette switch, from `cached_gradient_palette()`, with a separate cache per channel (`palette_hd_for_channel`).
- `palette_manual_colour()` does three things:
  - It adds the auto-shift in float (`h += hue_position`).
  - It scans for the two stops either side of `h`.
  - It interpolates with `t = (h-pos[i])/(pos[i+1]-pos[i])` and returns native CRGB16.
- It falls back to `ColorFromPalette` only when the cache is cold (`hd.count==0`).

**The fix in the shipping K1 source today** [FACT]:
- `SPECTRASYNQ_K1_FIRMWARE/visual/lightshow_modes.h:113-298`
  - Header at line 113: "HD PALETTE SAMPLING (2026-06-11, palette-resolution lane item 1)".
  - `palette_manual_colour` is at line 244.
- In git, it is buried in the fork root commit `ed56dfb5` (2026-06-23); see #73575. It originated in SensoryBridge-main 9.

**The 80-bin mode itself:**
- Proof on 2 Jul 2026, P115779: the legacy GDFT call was `ColorFromPalette(pal, palette_index_with_phase(uint8_t(freq_prog*255)), …)` (#73587). The HD path gave "roughly 8–12× more distinct colours".
- Migrated in commit **`c2738b88`** (2026-08-22, "paint C1/C2 colour in 16-bit after device PASS").
- It is now `light_mode_gdft.cpp:86`: `final_color = palette_manual_colour(pal, freq_prog, bin);`.

### Fix B — colour must not be transported or averaged; carry intensity only and colour at output [FACT]

**Lightwave-Ledstrip, 9 Feb 2026.** The Captain wrote (P11663): "colour (palette) inaccuracies/corruption … unable to display the palette colours accurate[ly] … saturating at least one or more of the R, G or B channels."

Two fixes failed first:
- A per-pixel proportional history scale (#28397).
- A weighted-centroid single lookup (#28398). The Captain's verdict: "still wack. Doesn't actually look any different."

**What resolved it** (obs #28399, #28400, #35053, in `BloomParityEffect.cpp`):
- `computeInjection()` returns `RGBf{bright,bright,bright}`, so the moving trail carries only brightness.
- "Palette mapping happens at final output stage … every LED receives one clean palette.getColor() call."
- The palette index is "spatial position (distance from centre × spread) + hueOffset + gHue".
- The Captain's response was "Holyshitballs — that is WILD" (P11668).

**K1 adoption:**
- `light_mode_bloom_bt.cpp` (#79225, commit `7b3bb992`, 2026-07-13) states: "Greyscale transport. The scroll state stores INTENSITY only; colour is applied at the output stage, so hues never compound down the trail."
- **It is NOT in `origin/main` or the current HEAD.** It exists only on `lane/gem-port-beat-pulse` and agent branches.

## HOW K1 MAPS PALETTE TO BINS AND LEDS TODAY (shipping source HEAD `68a95773`) [FACT unless marked]

- **Per-bin spatial modes** colour each bin by its position along the palette, then sample through HD `palette_manual_colour`:
  - Spectrum River: `hue = k / (analysis_bins-1)` with Nyquist-safe bins only (ghost bins 71–79 retired); `light_mode_spectrum_river.cpp:62-70`.
  - River v2 `:80`, Tempo River `:129`, River Walk `:179`, River Surge `:196`.
  - GDFT: `freq_prog` at `:86`.
- **Single-colour modes** (Bloom, Waveform family, Aurora, Comet) sample one palette position per frame:
  - Function: `palette_chroma_colour_with_offset` (`lightshow_modes.h:320-509`).
  - Hue: circular `atan2` centroid of `chromagram_pregate[12]`.
  - Weak frames: blend via `k1_vibrancy_blend_hue` (`:306`).
- **Particles** use `chromagram_centroid_hue()+offset` (`:589-616`).
