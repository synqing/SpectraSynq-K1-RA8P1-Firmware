# Palette mapping forensics: the K1 "over-averaging" bug, its fix, and the Titan

THE TITAN MUST ALWAYS BE VISUALISING MUSIC. This was read-only research: no device, serial port, broker or repository edits. Everything written here sits in this folder.

Picture: [`palette-mapping-explainer.png`](palette-mapping-explainer.png), regenerated by [`make_explainer.py`](make_explainer.py) from real palette data and real host-replay renderer frames.

## Plain English

**What the bug was.** On the K1, colour in the Bloom and Waveform family is picked from the palette using the music's 12 note strengths. These come from folding the 80 frequency bins into 12 notes. The K1 went wrong in two linked ways, both forms of "too much averaging":

1. **May 2026 (Sensory Bridge code that became the K1 firmware).** Waveform added together the palette colours of every active note. Mixing red, green and blue palette colours this way produces grey or white. Bloom had the opposite fault: it used only the single loudest note, so it could reach only 12 fixed spots on the palette.
2. **June–July 2026, in `SpectraSynq_K1_Firmware` itself.** On loud or dense music, the 12 note strengths came out nearly flat. A "sparseness gate" then zeroed them, and the palette position froze on one spot. The symptom was recorded as "palettes progressively duller; each palette a handful of colours." Louder music made it worse.

**How it was fixed.**
- **22 May 2026:** take one palette sample per colour, at a smooth position weighted by all 12 notes. Never add palette colours together.
- **2 Jul 2026, K1 commit `ae5d90a` (`K1_PALETTE_VIBRANCY_V1`):** read the note strengths *before* the gate. When the harmony is unclear, ease toward the live reading instead of freezing. It was checked by eye on the K1 at loud volume and passed on 3 Jul 2026. It is enabled in the production `k1_hardware` build. On dense music the number of distinct palette positions went from 2 to 11.

My recollection check: the record holds no "80-bin per-bin palette" bug. The 80 bins matter only because they are folded into the 12 notes. The averaging fault was in how those 12 notes became one palette position.

**Does the Titan have it now?**
- **Titan v8 (boot profile 8): no.** It already uses the fixed K1 rule. The palette position is read every frame from the pre-gate note strengths (`inhouse_waveform.cpp:159-168, 204-205`). On BOOM the colour moves in 95% of seconds.
- **Titan v9 (the P6 candidate, boot profile 9): yes, the same failure has come back by a different route.** v9 moves colour only when a "confidence" value is high. That confidence is multiplied by the *post-gate* tonality gate (`inhouse_waveform.cpp:157-158, 181, 592-594`), and on top of that colour can move at most 0.25 palette units per second. In the host replay of BOOM (room microphone):
  - the gate holds the colour still in 61% of music frames. At −6 / 0 / +6 dB that figure is 29% / 61% / 79%, the same louder-is-worse pattern as the K1 in July;
  - the colour moves noticeably in only 1% of seconds;
  - the whole strip wears one parked colour.

  The "restricted range" palette fold (`:562-568`) also makes positions c and 1−c give the same colour, which halves the colours v9 can reach.

**Proposal (NOT APPROVED):** make the v9 colour layer follow the K1 rule. Details are in the last section.

## Ship path (Captain directive)

1. **Already in source:** the K1 fix is in `SpectraSynq_K1_Firmware` (`ae5d90a`, enabled in `k1_hardware`). Titan v8 follows the same rule. Titan v9 does not.
2. **Remaining steps:** decide whether v9's slow colour layer is wanted. If it is, apply the proposal below. Then run the frozen colour-coverage metric on the 10-input replay corpus, then do the usual P6 gates and rtrace on the bench.
3. **Who acts:** the P6 effect-mapping lane implements and measures. The Captain decides whether v9 colour should be slow (a "harmony layer") or follow every frame like the K1.
4. **The flash that means shipped:** boot profile 9 built with the corrected colour layer, installed, and rtrace-scored on the Titan.

## Proposal for v9: PROPOSAL — NOT APPROVED

**Aim:** apply the proven K1 rule to the v9 colour layer, and keep v9's lighting and deposit work unchanged.

1. **Remove the post-gate gate from colour confidence** (`:592-594`). Replace `f(tonality_gate_)` with nothing, or with a pre-gate quiet guard like the K1 one (`maximum > 0.08`, already computed at `:161`). This applies the standing K1 rule.
2. **Replace "follow only when confident" with the K1 blend.** Each frame the target is `k1_vibrancy_blend_hue(centroid_, held, centroid_strength_)`, which is what `familyColour` `:307-313` already does. Level only scales brightness, never colour position.
3. **Raise or remove the 0.25 units/s follow cap and 0.6 s smoothing.** If a slow "harmony layer" is wanted, that is the Captain's design choice (see the decision below). Any smoothing must be short enough to pass the metric in point 5.
4. **Replace the `kRestrictedRange` triangle fold** with a one-to-one remap `p = lo + (hi−lo)·c`. This keeps the near-black exclusion without merging c and 1−c. A wrap seam then needs a decision: either allow the jump hi→lo, or use a palette whose ends meet.
5. **Frozen test metric** (host replay, 10-input corpus, both boards, music frames only):
   - (a) % of 1 s windows whose palette position spans > 1/32;
   - (b) entropy over 32 palette bins;
   - (c) per-bin hue fidelity: every lit renderer pixel's hue must lie within ΔE00 ≤ 3 of the authored palette curve (`offpal_px` already exists in the probe CSV);
   - (d) loudness coupling: −6 / 0 / +6 dB values of (a) must not fall as level rises.

   Pass bar: (a) and (b) within 10% of v8 on every input, (c) 0 off-palette pixels, (d) monotone non-decreasing. To show the guard can fail, it must go red on the current v9 default (it does: 1% against 95%) and on a planted fault that re-points the centroid at post-gate `observation_.chroma`.
6. **Do not** touch the 80→12 fold, the gate itself (chromatic modes still need it), the palettes, the 24/255 cap, or the gamma and output stages.

**Decision for the Captain:** should Titan v9 colour change at the speed of the harmony every frame, like the K1, or as a deliberately slow "harmony layer" that still never stalls on loud music?
